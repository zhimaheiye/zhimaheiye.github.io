Mumu模拟器开机自启动检测

问题描述

关于游戏日常的自动化，我之前一直采用这样的方式：将游戏脚本的启动程序快捷方式放在”shell:startup”文件夹下开机自启动，然后通过”启动模拟器并启动脚本“这一项使得脚本打开模拟器后自动连接运行。

游戏某次版本更新后，新版本的安装包无法在mumu12（旧版本编号）上运行，我不得不更新到当前的mumuV5，但这就导致了一个问题，这个版本的mumu模拟器无法稳定被清日常脚本启动。
主要的区别在于（模拟器这个我不懂，我只是根据自己的使用体验和理解来说）原来的版本是直接连接，新版本是在启动模拟器之后再单独启动其中不同的子设备。我可以为这个子设备新建快捷方式，如图所示

在把下面这个编号#0的模拟器快捷方式放进”shell:startup”文件夹后，某些时候是可以启动成功的，即脚本和模拟器都分别自启动然后连接起来，但并不稳定。
一方面是因为，原先的方式是由清日常脚本启动模拟器，方式是在脚本里设定模拟器的路径，脚本会等待模拟器60秒，并在连接成功后自动运行。但在后来的方式里模拟器并不是由脚本启动的，因此我只能选择启动脚本后直接运行，那么很多时候模拟器运行起来的时候脚本已经因为连接不上模拟器超时关闭了。
另一方面是有时候模拟器压根就启动不起来，原因不明，无法稳定复现。

比较好笑的是如果我在电脑刚启动的时候迅速点进来启动模拟器，那脚本就能连接上然后丝滑的运行，但这就跟我摆完挂机的愿望相违背了。
所以我需要另一个运行在模拟器和清日常脚本之外的程序，来检测和管理这两个的启动。

1.编写批处理文件

过程中遇到的问题:正确检测mumu模拟器进程

问题描述：之前的代码里实际的模拟器没有被启动，但模拟器的主进程是开机自启的，因此脚本误认为模拟器已经启动了。修改的逻辑如下（是ai写的我不太懂）

1. 检测逻辑改进

  • 原来只检测 MuMuNxMain 进程，但后台服务常驻，会误判为”已运行”
  • 现在检测三层：
    • 主进程是否存在
    • 设备进程 MuMuNxDevice 是否运行（真正的模拟器）
    • 可见窗口 是否存在

2. 启动参数修复

  • 原来：MuMuNxMain.exe（无参数）→ 只打开管理器，不启动模拟器
  • 现在：MuMuNxMain.exe -v 0 → 正确启动模拟器实例

2.任务计划程序

  1. 按 Win + R，输入 taskschd.msc 回车/或者在搜索框里搜索”任务计划程序“
  2. 右侧点击 “创建基本任务”
  3. 设置名称，例如MaaYuanAutoStart
  4. 触发器：当特定用户登录时
  5. 操作：启动程序
  6. 程序/脚本：C:\Users\Administrator\.qclaw\workspace\Run-MaaYuan.bat（这里要修改为批处理脚本的实际路径
  7. 起始于（可选）：C:\Users\Administrator\.qclaw\workspace（脚本所在文件夹路径
  8. 完成前勾选 “打开属性对话框”
  9. 在属性里：
  • 常规 选项卡：勾选 “使用最高权限运行”
  • 触发器 选项卡：编辑 → 勾选 “延迟任务” → 设置为 1 分钟

但是这就引出了一个问题，我原先使用任务计划程序是在我平时的笔记本电脑上的，开机必定会登录，但这个清日常的台式机是挂机的不会每次都查看，因此需要去除掉”登录“这一步

3.去除登录

Win + R → regedit → 回车打开注册表
找到”HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon“
修改或确认以下项目的值：

  • AutoAdminLogon = 1
  • DefaultUserName = Administrator
  • DefaultPassword = （你的密码，没密码就留空字符串）

这样就能跳过登录页面直接进桌面了

多设备同步

百度网盘（强烈不建议）

百度网盘的同步空间更适合用来同步“保存后释放”的文件，而不是obsidian这种实时编辑的文件，仓库内的保存和网盘同步都会经常出错。
而且百度网盘会在同步冲突时新建一个冲突文件，类似：“文件1_冲突文件_时间戳”这种格式，但obsidian只会读取原命名文件，所以有的配置会同步出错，手动改很麻烦的

把仓库文件夹右键设置同步，开机自启动之后就可以无感同步了。

本地抓取输入法输出

1. 需求描述

我最近有个需求：我每天会输出很多内容，但这些输出的内容大部分都浪费掉了。如果能让 AI 学习我输出的这些内容，把它整理成一个知识库，之后就能更好地跟我交流。

Cherry Studio 里的全局记忆很符合这个需求，但它最近坏了，暂时弄不明白原因。简单来说，就是想省掉“把自己的提示词复制一遍，粘贴到某个 AI 窗口里让它输出总结”的过程。于是想能不能从输入法下手。

2. 方案探索与对比

2.1 方案一：Obsidian + AI 插件

  • 尝试工具：Smart Connections。
  • 否决原因：
    1. 测试相关性搜索效果一般。
    2. 笔记都是有意识整理好的，我更希望能够进行全部的、没有筛选性的抓取。

2.2 方案二：Quicker + 本地 API

  • 方案逻辑：在任何窗口选中文本 -> 触发 Quicker 动作 -> 发送给 Ollama 提取 -> 存入本地文件。
  • 优点：灵活，覆盖所有软件，保留了“主动选择”的权利。
  • 否决原因：不够无感。还是需要“手动操作选择”，我不喜欢这种每次都要打断思路去操作一下的感觉。

3. 最终选择：Rime 输入法 + 挂钩日志

5. 后端处理：日志清洗与 AI 知识库构建

5.1 日志处理工具使用说明

5.1.1 概述

本工具将日志处理分为两个独立步骤：

  1. 本地合并处理 (merge_logs.py)：将零散的语音转录片段按时间戳合并成完整句子。
  2. AI 数据提取 (process_with_ai.py)：调用在线 API 对合并后的句子进行智能分析和提取。

5.1.2 工作流程

第一步：本地合并处理

  3. HTTP 和 HTTPS 都填写：http://127.0.0.1:7897（端口号根据你的代理软件而定）
